# NewsQuack v1.0 — Release Summary

> SP branch: `sp/01` · Released to master: 2026-11-01 (tag `v1.0`, commit `b6b8e20`) · Previous release: none — first release

## Overview

NewsQuack is a self-hosted .NET 10 service that polls RSS/Atom feeds and YouTube channels and delivers every new post to Discord via webhook. v1.0 delivers the reliability foundation everything later builds on: **at-least-once delivery** (a post may be delivered twice after a crash, never lost), **per-item error isolation** (a broken item is logged and dropped — it never kills the feed or the host), and **rate-limit-aware sending** (client-side pacing plus `429`/`Retry-After` handling).

## Highlights

- Multi-instance, single container — one config file describes any number of polling instances, each with its own feeds, check interval and webhook.
- At-least-once delivery — a post is marked delivered only after Discord answers HTTP 204; a crash can produce one duplicate post, never a lost one.
- Persistent deduplication — delivered and in-flight item IDs live in SQLite, so restarts never re-send old posts and slow drains never create duplicates.
- Rate-limit-aware sending — client-side pacing (default 3 s per webhook URL) plus exponential backoff that honors Discord's `Retry-After`, staying under Discord's per-webhook limit by construction.
- Discord webhook target with embed / forum / markdown modes and automatic one-shot fallback on channel-type mismatch.
- Dead-letter store with classified errors (`429`, `5xx`, `timeout`, `400-payload`) and an optional alerting webhook for failed posts.
- Feed error tracking — per-feed failure counters with exponential backoff and auto-removal of persistently failing feeds.
- Production-ready operations: health endpoints, graceful shutdown with WAL checkpoint, JSON-line UTC logging, anti-SSRF redirect validation on by default.

## New features & capabilities

**Configuration & operations**
- v2 config schema with total single-pass validation at boot — every error in one friendly list (exact JSON paths), exit code 1, no stack traces (T-002).
- `NEWSQUACK_*` env-var overrides for every config value; webhook tokens masked in all error messages (T-003).
- Structured JSON-line logging with UTC timestamps, later moved to Serilog with the frozen line format preserved and EF Core log noise capped (T-004, T-054 / #69).
- `/healthz` + `/readyz` health endpoints on a config-driven port (T-030).
- Graceful shutdown: stop schedulers → drain send queues within a bounded window → checkpoint the SQLite WAL (T-031).

**Fetching & parsing**
- Named HTTP clients with anti-SSRF redirect validation, on by default (T-005, T-058 / #76).
- Feed fetcher with a global HTTP throttle, user-agent cascade and robots.txt handling (T-010).
- Two-pass feed parser with per-item error isolation and strict UTC date normalization under hostile cultures/timezones (T-012; matrix tests T-042).
- Per-platform post builders: generic / YouTube / Reddit / GitLab (T-013; outputs pinned by T-043).

**Pipeline & delivery**
- Dedup engine with at-least-once semantics — skips items already delivered or still in flight (T-014; in-flight pending markers T-049 / #57).
- Post pipeline runner: ordered stages with per-stage failure policies, plus a drift-free per-instance scheduler on absolute slots (T-024).
- Per-instance send worker: exponential backoff with full jitter, `Retry-After` (header or body) honored as an absolute floor, bounded retry budget → dead letter (T-021; pinned by T-044).
- Persistent dead-letter store with classified errors and an optional system-webhook notifier (T-022).
- Per-feed error tracking: exponential backoff (30 s doubling, 6 h cap) and auto-removal of persistently failing feeds (T-016).

**Discord target**
- Discord webhook target — embed / forum / markdown modes, payload limits, fallback image, one-shot swap on channel-type mismatch (T-020). Telegram/Slack/Rocket Chat/generic webhooks are planned for later releases.
- Client-side webhook pacing: configurable minimum interval per URL (default 3 s ⇒ at most 21 requests per closed 60 s window); state shared across instances using the same URL, strictest wins (T-048 / #56; default raised by T-051 / #62).
- Feed attribution in every message — display name with URL fallback (T-052 / #63, T-053 / #67).

**Persistence & state**
- SQLite (WAL) state store: versioned migrations applied at boot, 30-day retention on delivered-item records, crash-safe in-flight markers wiped at startup (T-015; pending-marker migration T-049 / #57).

**Containerization & CI**
- Multi-stage Dockerfile (SDK → ASP.NET runtime, non-root user); CI with build-test, audit and docker-push jobs.
- Release images published to GitHub Container Registry as `ghcr.io/thebrutalx/newsquack` (multi-arch amd64/arm64), tagged per release; Node 24 action majors.

## Fixes

Notable bug fixes in this release (issue/PR references are pre-history-scrub numbering — see the Change log note):

- #48 / PR #49 — WAL checkpoint never ran on graceful shutdown (`StopAsync` received an already-canceled stopping token); fixed with its own bounded deadline plus a regression pin. Found by the integration smoke test.
- #51 / PR #52 — CI flake: 100 ms floor assertion without timer-granularity tolerance; fixed with the shared `ClockEpsilon` pattern (test-only).
- #55 / PR #58 — fresh-DB backlog delivered newest-first; now per-feed oldest-first (stable sort by publish date).
- #56 / PR #59 — no client-side pacing ⇒ 429 storm plus a ~30-min escalation block on backlog bursts; webhook requests are now paced at a configurable minimum interval.
- #57 / PR #60 — in-flight items re-enqueued by the next poll ⇒ duplicates under slow drain; in-flight pending marker plus idempotent dead letters.
- #71 / PR #72 — multi-section descriptions flattened into one wall of text; line structure is now preserved.
- #73 / PR #74 — two CI flakes from tight wall-clock budgets in scheduler tests; measurement-only hardening (test-only).
- #75 / PR #82 — uncapped HTTP response bodies (OWASP A08/A02); feeds capped at 8 MiB, Discord responses at 64 KiB.
- #76 / PR #83 — SSRF hardening: private-network redirect block on by default; unspecified addresses (0.0.0.0, `[::]`) blocked; https→http downgrades warn.

## Usage & configuration

- Docker quick start (multi-arch image; pin the versioned tag): `docker run -d --name newsquack -v /host/path/newsquack.json:/config/newsquack.json -v newsquack-data:/data ghcr.io/thebrutalx/newsquack:v1.0`
- Config file search order: CLI argument → `$NEWSQUACK_CONFIG` → `./newsquack.json` → `/config/newsquack.json`; boot-time validation collects every error and exits 1 with no stack trace.
- State database defaults to `/data/newsquack.db` (override with `NEWSQUACK_DATABASE`); keep the volume across upgrades — migrations run at boot.
- Every config value can be overridden via `NEWSQUACK_*` env vars (env always wins over the file). New in v1.0: the per-instance pacing key `instances[*].discord.minSendIntervalSeconds` (1..60, default 3 s when omitted) — e.g. `NEWSQUACK_INSTANCES__0__DISCORD__MINSENDINTERVALSECONDS`.
- Optional dead-letter alerting: set `NEWSQUACK_DEADLETTER_WEBHOOK` to an absolute http(s) webhook to receive one JSON notification per dead letter.

Full key reference, env-var scheme and operational variables: see the [README](https://github.com/TheBrutalX/NewsQuack/blob/master/README.md).

## Known limitations

- Dead-lettered items are re-attempted on every poll cycle; there is no purge/retention tooling for dead letters yet (follow-up planned).
- Feed state is not advanced at confirmation — each poll re-parses the whole feed. Dedup plus in-flight markers keep this correct; state advancement is planned for M2.
- Per-feed oldest-first ordering only — no global cross-feed chronology across an instance's feeds.
- One webhook URL per instance (no fan-out); instances sharing the same URL share pacing state, and the strictest (smallest) interval wins.
- Under sustained Discord 429 rate limiting, the single-reader worker can hold the per-instance queue at capacity (100) — correct backpressure; at-least-once semantics guarantee re-delivery.
